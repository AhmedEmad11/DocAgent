# Security review (Phase 7, deployment items updated in Phase 8)

Date: 2026-11-21. Scope: the API as of Phase 6 plus the changes in Phase 7. Method: reading all endpoint, auth, data-access, upload, LLM and ingestion code against the OWASP API Security Top 10 (2023) and SRS SEC-1..SEC-8, PRIV-*, then fixing what was found, each fix with a test. NuGet audit (`dotnet list package --vulnerable --include-transitive`): no vulnerable packages.

Status values: **Fixed** (changed in Phase 7, test named), **Verified** (reviewed, no defect, existing test named), **Accepted** (known residual risk, reason given), **Fixed in repo, pending deployment** (Phase 8: the change and its test are in the repository, but it only takes effect once the service is deployed and the setting is verified live; verification is part of the Phase 8 acceptance check).
Severity is the author's judgement of impact and likelihood for a public multi-tenant service on free tiers: High, Medium, Low, Info.

No finding allowed one tenant to reach another tenant's data. The medium findings are resource-consumption and deployment-hardening gaps.

## Not changed, on purpose
- **Hosted provider calls: exactly one retry (stakeholder decision after Phase 7, REL-2).** One retry on a 5xx (incl. Anthropic 529) or a connection failure, with a short backoff (`Retry-After` honoured, capped at 2 s), implemented once in `ProviderHttpHandler`. A 429 or other 4xx is never retried (it would worsen the limit or repeat a billed call), nor is a response that has started streaming. The retry is below the quota charge, so the demo allowance is charged once per question; the demo primary gets the one retry, then the fallback model, and a 429 goes straight to the fallback. The key is not logged (there is still no logging handler). Residual risk: a 5xx after the provider began generating may bill a second generation; accepted. Tests: `ProviderRetryTests`, `DemoChatClientTests`, `DemoModeTests`.
- **Ollama** (development only) now retries connection failures and 502/503/504 (REL-2), since a local restart or model load is the common transient there and nothing is billed.

## Residual risks for Phase 8 (status after the repo-side work)
1. `AllowedHosts`, forwarded headers, the operator-key secret and the key ring: **fixed in repo, pending deployment** (S-18, S-20, S-32; the operator key is already required at startup).
2. One API replica: **done in `infra/main.bicep`** (`maxReplicas: 1`, with the reason in a comment); verify live that only one replica runs. Scale to zero adds a cold start and an ingestion in progress is not kept alive by traffic (it resumes after the stale-job lease when the app wakes again): see DEPLOYMENT.md "Scale to zero".
3. Memory and CPU limits on the container (S-10): **done** (0.5 vCPU / 1 GiB).
4. Neon free storage (0.5 GB) cannot hold even one user at the maximum (200,000 chunks is about 1.6 GB with indexes); see the PERF-2 numbers in PROGRESS. **Still open**: a product question (storage limits per user).
5. Certificate rotation for the key ring is a manual procedure and not tested live.
