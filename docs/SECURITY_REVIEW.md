# Security review (Phase 7)

Date: 2026-11-21. Scope: the API as of Phase 6 plus the changes in Phase 7. Method: reading all endpoint, auth, data-access, upload, LLM and ingestion code against the OWASP API Security Top 10 (2023) and SRS SEC-1..SEC-8, PRIV-*, then fixing what was found, each fix with a test. NuGet audit (`dotnet list package --vulnerable --include-transitive`): no vulnerable packages.

Status values: **Fixed** (changed in Phase 7, test named), **Verified** (reviewed, no defect, existing test named), **Accepted** (known residual risk, reason given), **Deferred (Phase 8)** (needs the deployment environment).
Severity is the author's judgement of impact and likelihood for a public multi-tenant service on free tiers: High, Medium, Low, Info.

## Summary
| Severity | Found | Fixed | Verified (no defect) | Accepted | Deferred (Phase 8) |
|---|---|---|---|---|---|

No finding allowed one tenant to reach another tenant's data. The medium findings are resource-consumption and deployment-hardening gaps.

## Findings

| S-01 | API2 / API5, authN and authZ | Nothing guaranteed that every endpoint had a deliberate auth decision; a new endpoint without `RequireAuthorization` would silently be public. | Medium | **Fixed** | `EndpointInventory` + `HardeningTests.Every_mapped_endpoint_has_an_explicit_auth_decision` (fails for any new, missing or differently protected endpoint); `Protected_endpoints_answer_401_to_anonymous_callers_and_403_to_unconfirmed_users` calls every protected endpoint. |
| S-02 | API1, BOLA / tenant isolation | Reviewed every data path. | S-03 | API3, mass assignment / property exposure | Requests bind to dedicated records (`AskRequest`, `SaveKeyRequest`, ...), never to entities. Identity's `register` takes only email and password. Responses are dedicated records (no `UserId`, no key material). | Info | **Verified** | `HardeningTests.Registration_ignores_extra_fields_so_an_account_cannot_confirm_itself_or_pick_roles` |

| S-06 | API4, expensive requests | No cap on concurrent ask / stream / summary / compare per user. Each runs an in-process ONNX embedding and an agent loop of up to 120 s on a shared container, whatever the user's provider. Demo users are bounded by the daily quota and the shared throttle (S-08); BYOK users were not bounded at all. | Medium | **Fixed**: per-user concurrency cap (`RateLimiting:Ask:MaxConcurrentPerUser`, 4) over all four endpoints. No per-minute request rate was added: the SRS asks for none and BYOK users pay their provider themselves (see PROGRESS, choices). | `HardeningScenarioTests.A_second_question_while_one_is_running_is_refused_with_429_and_the_slot_frees_up_afterwards` |
| S-07 | API4, storage / index size | No limit on the chunks one document can produce. A 25 MB text file is about 16,000 chunks; 100 such documents are 1.6 million chunks (about 8 GB with indexes), far beyond the Neon free tier (SRS C2) and without a defined worst case for PERF-2. | Medium | **Fixed**: `Documents:Ingestion:MaxChunksPerDocument` (2000, about 3 MB of text); a longer document is `Failed` with a "too long, split it" reason, checked before embedding. | `HardeningTests.A_document_with_more_chunks_than_the_limit_fails_with_a_clear_reason_before_any_embedding` |
| S-08 | API4 / API6, shared demo key | The operator's OpenRouter key had no local throttle: a few users could exhaust the free models' shared per-minute limit and every later request would still go out to be refused. | Medium | **Fixed**: `Llm:Demo:GlobalRequestsPerMinute` (20, all users, 0 = off), 429 `demo_rate_limited` + `Retry-After`, before the daily quota is charged and before any provider call. | `DemoGlobalThrottleTests` (unit), `DemoGlobalThrottleEndpointTests` (refused requests cost no question and no provider call; other endpoints unaffected) |
| S-09 | API4, DOCX | Zip bomb: declared uncompressed size and entry count are checked at upload and again at parse (a lying central directory cannot make .NET inflate more than the declared size). | S-10 | API4, PDF | PdfPig cannot be cancelled inside one page. The 60 s parse timeout abandons the work (the worker moves on) but a pathological page keeps burning a thread until it ends. Bounded by the page cap (2000), the 25 MB file limit and the confirmed-email requirement. | Low | **Accepted**; process isolation or container CPU limits are a Phase 8 option. | `ExtractionTests` (page cap, timeout path) |
| S-11 | Upload type confusion | Type is detected from content (PDF magic, ZIP with the Word parts, valid UTF-8 without NUL); the extension must agree; the client's content type is ignored. | Info | **Verified** | `FileTypeSnifferTests`, `DocumentIngestionTests` |
| S-12 | Upload filename | Names are sanitized (control characters, path parts, length) and stored only for display; original files are never written to disk. Names are neutralized in prompts. | Info | **Verified** | `FileNameSanitizerTests`, `QaPromptBuilderTests` |

## Not changed, on purpose
- **Hosted provider calls are not retried** (REL-2 says "429/5xx are retried with backoff", Phase 5 turned retries off). Reason: these calls are billed to the user's key or take the shared demo key's limited quota; a retry after 429 makes the provider limit worse and the agent loop can be many calls long; a retry after a 5xx may repeat a billed generation. The demo already has the fallback model (DEMO-4), and the user gets a specific error with `Retry-After` (KEY-7). Kept; this is a stakeholder question (see the Phase 7 entry in PROGRESS).
- **Ollama** (development only) now retries connection failures and 502/503/504 (REL-2), since a local restart or model load is the common transient there and nothing is billed.

## Residual risks for Phase 8
1. Set `AllowedHosts`, `ForwardedHeaders:Enabled=true`, the operator key secret, a persistent Data Protection key ring stored apart from the database.
2. Run one API replica (job recovery at startup assumes one worker instance; the stale-job check protects against a second one only after the lease).
3. Memory and CPU limits on the container bound a parse that outlives its timeout (S-10).
4. Neon free storage (0.5 GB) cannot hold even one user at the maximum (200,000 chunks is about 1.6 GB with indexes); see the PERF-2 numbers in PROGRESS.
