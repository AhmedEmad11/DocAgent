### 2026-11-12: Phase 4 implemented and committed (independently re-run: build 0 warnings, 370 tests pass; Phase 3 CI run 43284631854 green)
- **Packages (Infrastructure):** `Microsoft.Agents.AI` **1.28.0 (stable)** (Microsoft Agent Framework; pulls `Microsoft.Agents.AI.Abstractions` 1.28.0, needs `Microsoft.Extensions.AI` 10.11.0, which was already in use). No other new packages; the eval project reuses the integration-test packages (xunit, Mvc.Testing, Testcontainers).
- **Agent design.** `AgentQaService` builds a `ChatClientAgent` over the route's `IChatClient` (`UseProvidedChatClientAsIs`) with five function tools made by `AIFunctionFactory` from C# methods (`AgentToolbox`): `search_documents(query, documentIds?)`, `get_chunk_context(sourceIndex, before, after)`, `get_document_outline(documentId)`, `summarize_document(documentId, focus?)`, `compare_documents(documentIdA, documentIdB, focus?)`. `documentId` accepts the id (shown in search results) or an exact file name. No tool takes a user id; all reads go through the tenant-filtered `AppDbContext`/`IRetriever`; documents are addressed only through the run's document list (the caller's Ready documents, narrowed by the request's `documentIds`) and chunks only through numbers the run's `SourceRegistry` handed out. Per-request `SourceRegistry`: same chunk = same index across all tools, so `[n]` in the answer maps to one chunk; a chunk shown before is referred to as `note="already shown above"` instead of being sent twice. Tool results are `<source index documentId file page section>` blocks, neutralized like the Phase 3 prompt, headed by "untrusted document content".
- **What the framework could not do, and the wrapper:** Agent Framework / `FunctionInvokingChatClient` only has a hard iteration limit, not "stop calling tools but still answer" (QA-11). Added (1) `CountedFunction` (a `DelegatingAIFunction` around every tool): counts the call, refuses calls beyond the cap with a fixed message (also for several calls requested in one model turn), turns exceptions into a short error text (exception type logged, never its message), records an activity per call; (2) `ToolLimitChatClient` between the function-invoking layer and the real client: once the cap, the context budget or the soft deadline (70% of the timeout) is reached it removes the tools from the request and appends "Search limit reached ... answer now", so the model answers from what it has. `incomplete=true` and an "answer may be incomplete" note (EN/AR) when the cap was reached/used, the context budget was used up, the soft deadline passed or a nested summary/compare was cut by time. A run that ends without text after tool calls gets one more model call without tools. The hard timeout (`Limits.Timeout`) gives 504.
- **Context budget (not in the brief, needed):** gemma4 has NumCtx 8192 and Ollama silently drops the oldest messages on overflow (the system prompt would go first). `Agent:ContextBudgetTokens` (3600, embedding-tokenizer tokens) limits the source text the tools put into the conversation; when used up the tools are withdrawn like at the cap.
- **QA-4 decomposition:** by instruction, no planning step: the system prompt says to run one short keyword search per part of a multi-part/multi-document question. Measured on the 8 multi-part and 5 cross-document eval questions: 13/13 correct, 1.1 and 1.8 searches on average (the model does split: e.g. router address + vacation days = 2 searches, one search when the parts sit in the same document). A separate planning call would add 2-4 s per question; not needed at this accuracy, so not built. No ablation without the instruction was run.
- **QA-3 re-query:** also by instruction (at most two more searches with different words/the other language when results are weak); eval: en-10 ("Falcon portal project day to day" -> manager Laura Chen) and the Arabic question about the English trial document both needed 2-3 searches and pass; single-pass fails exactly these two (see below).
- **QA-5 verification:** `AnswerVerifier`, a separate model call with a strict JSON schema `{claims:[{id, supported, source}], answersQuestion}`. The draft is split into sentences/list items (a marker after the full stop stays with its sentence); every sentence that carries a citation is a claim, shown to the verifier together with the full text of the sources it cites (untrusted-data delimiters) and the question. Unsupported claims (and claims the verifier does not mention) are cut out; a supporting source other than the cited one is added to the sentence; if nothing survives, or `answersQuestion` is false, the response is `notFound`. A draft without any citation, or with no retrieved source at all, is never accepted. An unusable verifier reply is retried once, then the draft is kept unchecked (logged as a warning; open point: fail-open vs fail-closed). `answersQuestion` was added after the first eval round: gemma wrote "the documents do not specify X, they only mention Y [2]" for an unanswerable question and the claims checked out, so the draft had to be rejected for not answering. The agent signals "nothing found" with a leading `NOT_FOUND` token (final reply is plain text, not JSON; the schema is only used for the verifier).
- **QA-9 pre-check decision:** the Phase 3 "nothing >= MinScore -> notFound without LLM" check is not applied to the raw question in agent mode, because reformulation can find what the raw question misses (en-10). Instead: if no tool call ever retrieved a source, the answer is `notFound` with no draft/verification call (unanswerable questions cost 1-14 s, 0-3 searches). `Qa:Mode=SinglePass` keeps the old pre-check.
- **Seeded first search:** not done; the model calls `search_documents` first by itself in all eval runs except obvious off-topic questions ("who won the 2018 World Cup" -> 0 tool calls -> NOT_FOUND, which is correct but means the instruction "always search" is not guaranteed).
- **Limits (QA-11):** `LlmRoute` has a new `Limits` (`AgentLimits(MaxToolCalls, Timeout)`); `OllamaChatClientFactory` fills it from `Agent:Limits:Development` (10 calls / 120 s). `Agent:Limits:Demo` (4 / 60 s) and `Agent:Limits:Byok` (10 / 120 s) are defined and bound, unused until Phases 5-6. Other agent settings: `SearchTopK` 5, `ContextBudgetTokens` 3600, `MaxOutputTokens` 1024 per agent turn (a degenerate-output turn took 50-70 s in 2 of ~10 runs of one question before this cap), `SoftDeadlineFraction` 0.7, `MapBudgetTokens` 2800, `WorkflowMaxOutputTokens` 900.
- **`/api/v1/ask`:** same request, 400/409/403/503/504 semantics; response adds `incomplete` (bool), `toolCalls` (int) and `notices` (extraction notices, DOC-11, of the cited documents; `[]` if none). `Qa:Mode` = `Agent` (default) | `SinglePass`. If the agent loop throws anything other than "model unreachable" or "timeout", the question is answered by the single-pass pipeline (logged as a warning with the exception type). `AskService` is the entry point.
- **Summary / compare (QA-6, QA-7):** `POST /api/v1/documents/{id}/summary` (body optional `{focus?}`, <= 500 chars) and `POST /api/v1/documents/compare` (`{documentIdA, documentIdB, focus?}`); EmailConfirmed; 404 for foreign/unknown documents (identical response), 409 when not Ready, 400 for same ids/missing ids/long focus, 503/504. `DocumentWorkflows`: the document's chunks in `Ordinal` order are batched to `Agent:MapBudgetTokens` (2800 embedding tokens, about 4k gemma tokens, so a map call stays well under 8192), each batch -> bullets with `[n]` markers (registry numbers of the chunks), partials are merged (hierarchically if needed), a document that fits one batch takes one call. Compare: each document is condensed to topic-labelled bullets, then one call aligns them by topic (same/different/only in one) citing both documents, referring to them by file name. Summaries/comparisons are written in the language of the focus, else of the document. Response is the /ask shape (`toolCalls` 0, `notFound` false). On the route timeout, partial results are returned (`incomplete: true` + note) if at least one part finished, else 504. Summaries are not run through the verifier (QA-5 is about answers). The agent can also call both as tools (they get half of the remaining time).
- **Streaming (QA-10):** `POST /api/v1/ask/stream` (SSE, same validation/status codes as /ask before the stream starts). Events: `searching`, `tool_call` (data `{"tool":"<name>"}`), `verifying`, then `answer` (the /ask JSON) or `error` (`{status,title}`). The answer arrives whole after verification, not token by token (verification has to finish first). Verified in-process with a fake model and once per eval run against the real model (`searching > tool_call > verifying > answer`).
- **Telemetry (OBS-1, SEC-2):** activity source `DocAgent.Agent`: `agent.run` (tool_calls, sources, citations, stop_reason, incomplete, not_found), `agent.tool` per call (tool name, duration, result size, refused/error type), `agent.summarize`, `agent.compare` (chunk counts). - **HNSW check (EXPLAIN, `RetrieverIndexTests`, two users x 1500 chunks):** the query shape *can* use `IX_Chunks_Embedding` ("Index Scan using IX_Chunks_Embedding, Order By: Embedding <=> ..., Filter: UserId = ...") but, with the btree on `UserId` present, the planner chooses `IX_Chunks_UserId` plus an exact sort of that user's rows, at this size and also with `enable_seqscan=off`. That is correct (exact results) and fast for one tenant's rows; the planner switches to HNSW by itself when it estimates it cheaper (large tables). The test drops `IX_Chunks_UserId` to prove the HNSW path works with the tenant/status filters. Not tuned further; revisit in Phase 7 with a large dataset.
- **Hybrid measurement** (`RetrievalQualityTests`, 28 questions: 10 English paraphrase, 8 English exact-term, 6 Arabic paraphrase, 4 Arabic exact-term; corpus = 8 hand-written docs + 144 near-duplicate distractor paragraphs that differ only in an invoice number / error code / model number / form id; chunks about 1 paragraph each; MinScore 0). Recall@1/3/5/8, all questions: **vector-only 89 / 93 / 96 / 96 %, hybrid 100 / 100 / 100 / 100 %**. Exact-term questions: vector-only English 89/89/100/100, Arabic 33/67/67/67; hybrid 100 % everywhere. Paraphrase questions: 100 % both. Without distractors the corpus was too easy (vector 100 %), so the distractors are the meaningful part. A first hybrid version (OR of all words, `ts_rank_cd`) was worse than vector-only on some questions: Postgres full-text ranking has no IDF, so common words flood the list. The final version uses full text for strong exact evidence only: a chunk must match **all** significant question words, or all words containing a digit (codes, numbers); everything else is left to the vectors. **Default `Retrieval:Hybrid=true`.** Fusion: reciprocal rank fusion, k=60.
- **MinScore:** measured cosine of the answer chunk for the 28 questions: min 0.813, p10 0.832, median 0.873; top-1 for 10 unanswerable questions: median 0.786, max 0.837 (e5 scores are compressed into roughly 0.7-0.95, so the two ranges overlap a little). `Retrieval:MinScore=0.80` (just under the lowest answer score; rejects 6 of 10 unanswerable questions without an LLM call, the model handles the rest); `FullTextMinScore=0.75` for chunks found only by an exact-term match. Based on a small corpus: re-measure with real user documents.
